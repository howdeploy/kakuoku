# Backend и эксплуатация Kakuoku

Общий путь запуска веб-версии на Windows, Linux и macOS — Docker Compose;
требования к хосту и настройка папки описаны в [deployment.md](deployment.md).
Раздел ниже относится к дополнительному Linux-помощнику переноса, а не к
обязательной зависимости веб-приложения на всех ОС.

## Локальный перенос хранилища

`host/index.mjs` запускается на Linux командой `npm run host`, отдельно от
контейнера приложения. Он использует только стандартную библиотеку Node 24+
и локальный Docker CLI, закрепляя Unix socket выбранного Docker context.
Удалённые Docker endpoints, произвольные команды и чужие override-файлы
не поддерживаются. Сервис привязан к `127.0.0.1:3102`; Host и Origin разрешены
только для локального приложения на 3101. Изменения требуют JSON и отдельный
случайный токен, возвращаемый только разрешённому Origin; секреты в логи не пишутся.

API помощника: `GET /storage` → `{token,storage,job}`,
`POST /storage/plan {destination}` → `{plan}`, `POST /storage/move {id}` →
`{job}` (202), `POST /storage/recover {}` → `{job}` (202). План действует
пять минут, привязан к контейнеру и конфигурации; повтор ID не запускает копию
операции. Закрытие UI не останавливает работу. UI опрашивает состояние;
после перезапуска приложения его токен сессии обновляется.

`GET /api/storage` в приложении возвращает `{demo,paused,moveId}`.
`POST /api/storage/pause {id}` запрещает перенос при активном ответе,
превью, сортировке или HTTP-операциях и затем блокирует остальные API.
`POST /api/storage/resume {id}` проверяет ID и снимает блокировку.
На новом месте `.kakuoku-move.json` включает блокировку уже при старте,
до получения пользовательских запросов. Эти API не открывают файлы по пути
от клиента, не управляют Docker и не добавлены в инструменты модели.

Помощник останавливает только Compose-сервис `app`, копирует весь `/app/data`
из остановленного контейнера в приватный `.data/host/moves/<id>/data`,
проверяет SQLite `quick_check`, запрещает ссылки/специальные файлы и сверяет
SHA-256 всех файлов новой копии. Перед переключением файлы синхронизируются.
Новая папка должна быть пустой, вне проекта и прежнего хранилища; родитель
существует и доступен для записи. Корень диска и домашняя папка целиком запрещены.
Владелец данных 1000:1000 соответствует Compose; это устанавливает одноразовый
контейнер того же образа, с read-only корнем, без сети, Docker socket и иных
хостовых каталогов, с `cap_drop ALL` и единственной capability CHOWN.
Диски без Linux-владельцев/прав и fsync не поддерживаются.

Локальный `compose.override.yaml` переключает единственный data mount на
выбранную папку с `create_host_path:false`; он исключён из Git и build context.
Обычный Compose подхватывает его и после перезапуска. Журнал в `.data/host`
сохраняет этап и прежнее подключение. Изменения конфигурации/образа вне
помощника останавливают перенос. Новое приложение допускает записи только
после сохранения этапа committed; восстановление после этого этапа продолжает
новую установку, а не возвращает устаревшие данные. До committed ошибка
возвращает прежнее подключение; при невозможности безопасного восстановления
UI требует явного продолжения. Ни исходное хранилище, ни копия не удаляются.

Проверка на отдельном синтетическом Compose-проекте подтвердила перенос
сообщений, BLOB-фото, файловых вложений и настроек, сохранность исходного
volume, повтор ID без второй операции и обычный Compose с новым подключением.
Восстановление после committed сохранило сообщение, добавленное после переноса;
занятая после предпросмотра папка не была перезаписана, приложение вернулось
к прежнему подключению. В helper HTTP проверены разрешённый Origin, отказ
чужому Origin и отказ операции без токена. Браузер, перенос рабочих заметок
и платные запросы в этих проверках не использовались.

Обновлённый образ установлен на прежнем рабочем volume после полной
остановленной резервной копии. Все прежние строки таблиц, включая настройки
и ключи, совпали по хешам; новые столбцы проверялись отдельно. HTTP UI,
новые JS/CSS, контракт тегов, API хранилища и подключение помощника доступны.
DNS контейнера разрешает адрес AI через штатную конфигурацию Docker, без
закреплённого DNS в Compose. Рабочие заметки на другую папку не переносились.

Поддержка тегов — 2026-11-02: `notes.tags` —
JSON-массив, добавляемый миграцией со значением `[]`, без переноса данных.
GET настроек возвращает `tags`, PATCH принимает набор из максимум 64 уникальных
тегов до 24 символов; имена нормализуются в NFKC и нижний регистр, допустимы
буквы, цифры, дефис и подчёркивание. Сохранение настроек и удаление из заметок
тегов, отсутствующих в новом наборе, выполняются в одной SQLite-транзакции;
FTS для изменённых заметок обновляется в ней же. `/api/notes?q=...` поддерживает
точные `#теги` (несколько — пересечение) вместе с текстом. Обычный FTS также
индексирует теги. GET заметки/списка возвращает `tags` массивом.

AI-превью возвращает JSON `{summary,tags}`; сортировка — `tags` для каждой
новой сводки. Проверяются уникальность, принадлежность набору и количество
3–5 (либо количество доступных тегов, если их меньше). Неверный ответ не
заменяет прежнее превью. Превью и теги записываются атомарно с проверкой
revision, настройки набора входят в ключ кэша; удалённые во время запроса теги
не восстанавливаются при его завершении. Передаётся только общий набор имён
тегов и текущая заметка; scope модели и web tools не расширены. В демке и
режиме notes новых запросов нет. Тесты проверяют нормализацию, точный поиск,
пересечение тегов, сохранность сообщений/ключей и сброс ключа кэша при удалении
назначенного тега. Реальные модельные и UI-проверки не выполнялись.

Этот документ описывает код и конфигурацию. По запросу пользователя образ
собран и запущен; проверены HTTP UI/API и графические файлы. SSR-проверка
Markdown подтвердила основные элементы форматирования, безопасные ссылки
и отсутствие активного HTML/внешних картинок. Линтер, typecheck, браузер,
Electron и платные API-запросы не запускались. Ожидание реального AI и полная
функциональность не проверены; стойкость изоляции в Docker не подтверждена.

## Запуск и данные

Требуются Docker Engine и Compose v2 на Linux либо Docker Desktop в режиме
Linux-контейнеров на Windows/macOS. Один сервис `app`, процесс Node 24,
встроенная SQLite/FTS5, статический frontend. Redis и дополнительные серверы
не нужны. Команды выполняются из корня клонированного репозитория.
При наличии прежних данных сначала выполните [переход](rename-migration.md).
Для первой установки без прежнего production-хранилища:

```sh
docker volume create kakuoku-production-data
docker compose build --pull
docker compose up -d
```

Приложение: http://localhost:3101; HTTP API на том же origin.
Дизайн-демо запускается отдельно через `npm run dev` на 127.0.0.1:3100.
Не нужно останавливать демо для работы приложения.

```sh
docker compose stop
docker compose start
docker compose logs --tail=100 app
```

Политика `unless-stopped` перезапускает аварийно завершившийся сервис, но
уважает явную остановку. Наличие runtime-файлов Docker/Podman не проверяется.
`KAKUOKU_PRODUCTION=1` разрешает production-режим, а не доказывает изоляцию.
Не используйте этот флаг для запуска реального приложения на хосте.

По умолчанию постоянное хранилище — external volume **kakuoku-production-data**
(либо существующий volume, выбранный через `KAKUOKU_DATA_VOLUME`), подключённый
в `/app/data`. Если его нет, Compose сообщает ошибку и не создаёт пустой volume.

Дополнительный `compose.override.example.yaml` позволяет вместо volume
подключить свою папку через `KAKUOKU_DATA_DIR` из локального `.env`.
Фактические пути остаются вне репозитория и образа. Шаблон не включается
автоматически и не переносит данные; см. [порядок настройки](deployment.md#своя-папка-данных).

| Содержимое | Расположение |
|---|---|
| Заметки, сообщения, FTS5, профиль, настройки, ключ, результаты сортировки | `kakuoku.sqlite` и служебные WAL/SHM SQLite; прежнее имя автоматически поддерживается для существующих данных |
| Фото старого HTTP-контракта | BLOB в SQLite |
| Потоковые вложения | `media/<внутренний UUID>`, метаданные/связи в SQLite |

Production не использует `.data/demo`, не сидирует примеры, не принимает
`/api/feedback`; импорт Agentation заменяется пустым модулем при контейнерной
сборке. Ни демобаза, ни `.env`, ни node_modules хоста не входят в build context.
Ключ вводится в настройках, хранится в SQLite **без шифрования на диске**,
GET возвращает только `hasApiKey`. Сохранение настроек не проверяет подключение.
Compose не передаёт ключ в environment. Для нестандартных запусков сохранён
серверный `GHOSTMETAL_API_KEY` fallback, отключаемый явным удалением ключа
в настройках. Не задавайте секреты через `VITE_`.

Ограничения Compose: UID/GID 1000, read-only корень, единственный data mount,
tmpfs `/tmp` 64 МиБ с noexec/nosuid/nodev, стандартный `/dev/shm` ограничен
16 МиБ. RAM/swap 768 МиБ, CPU 2, pids 64 (включая init и медиапроверку),
дескрипторы 1024, core dumps отключены, capabilities сброшены,
no-new-privileges включён. Нет privileged, host network, устройств, домашней
директории, socket Docker/Podman и SSH-agent. Порт опубликован только на
127.0.0.1. Docker bridge сохраняет исходящий интернет для AI/исследований;
egress firewall не реализован. Общая с хостом ОС остаётся границей доверия.
Приложение рассчитано на одного пользователя; не публикуйте его наружу.

## Жизненный цикл и резервная копия

Остановка, пересоздание и `docker compose down` не удаляют volume.
Явное удаление заметки удаляет её сообщения и ненужные файлы; вложения,
используемые общей заметкой, сохраняются. Закрытие пустого черновика удаляет
его неотправленные вложения. Загрузка без отправки сообщения остаётся
неотправленным вложением до явного удаления или удаления заметки.
Никаких TTL, очистки на старте, удаления старых заметок или сборки мусора нет.

Сначала остановите приложение, затем скопируйте **весь** каталог (не только
основной файл SQLite). Пример с новым, ещё не существующим каталогом копии:

```sh
docker compose stop
mkdir -p .data/backups
docker compose cp -a app:/app/data ./.data/backups/kakuoku-backup-YYYY-MM-DD
docker compose start
```

Копия содержит API-ключ и личные данные, храните её приватно. Команда копирует
из остановленного контейнера на хост; дополнительных bind mounts не требуется.
Убедитесь в наличии копии перед обновлением. Затем:

```sh
docker compose build --pull
docker compose up -d --no-deps app
```

Миграции добавляют структуру в существующую базу. Не используйте одновременно
несколько серверов с одним volume. Для возврата к старой версии нужен её образ
и соответствующая резервная копия; автоматического downgrade схемы нет.
Восстановление в **новый пустой** volume: явно создайте его через
`docker volume create kakuoku-production-data`, выполните `docker compose create`, затем
`docker compose cp -a ./.data/backups/kakuoku-backup-YYYY-MM-DD/. app:/app/data` и
`docker compose start`. После копирования UID/GID файлов должны быть 1000:1000;
при несовпадении потребуется восстановить владельца отдельной административной
операцией. Флаг `-a` сохраняет владельцев при копировании; файловая система
резервной копии тоже должна их сохранять. В заполненный volume копию не
накладывайте: сначала отдельно решите
судьбу существующих данных. Эти процедуры подготовлены, но не запускались.

Удалить приложение, оставив данные:

```sh
docker compose down
```

Отдельное явное **безвозвратное удаление всех production-данных**:

```sh
docker compose down
docker volume rm kakuoku-production-data
```

При `KAKUOKU_DATA_VOLUME` сначала установите фактическое имя volume: приведённая
команда удаления относится только к имени по умолчанию.
Не используйте `down -v` или volume prune при обычном обновлении. Резервные
копии, демобаза и старые Podman-контейнеры этим не удаляются. Автоматического
импорта из прежнего writable layer нет; нужный старый контейнер не удаляйте.

Запись файла синхронизируется перед фиксацией его метаданных в SQLite.
Между файловой системой и SQLite нет общей транзакции: аварийное завершение
может оставить неподключённый файл; при удалении заметки — остаточный файл.
Такие файлы не раздаются API и не очищаются автоматически. Ошибка обычной
незавершённой загрузки удаляет только временные байты этого запроса.
Физическое стирание блоков диска и удалённых страниц SQLite не гарантируется.

## Права AI

HTTP API приложения доступен пользователю, а **не модели**. В адаптере нет
универсального HTTP, shell/exec, read_file, SQL, браузера/CDP, MCP и файловых
инструментов. Модель не получает session token, путь к volume, содержимое
окружения или API-ключ. Ключ использует только серверный транспорт.

| Операция | Серверная область данных и права |
|---|---|
| Ответ в чате | Только snapshot текущей заметки: переписка, постоянное имя, метаданные вложений; при включённом vision — до 4 подготовленных изображений этой заметки |
| Превью | Только текущая заметка; модель предлагает текст до 700 символов; запись сервером с проверкой ревизии |
| Явная сортировка | Snapshot всех сохранённых заметок; строгая схема групп, проверка каждого source ID, непересечения, ревизий и merge key; новые заметки, без удаления исходников |
| `read_url({url})` | Только research; один строковый аргумент до 2048 символов; публичный HTTPS:443; GET HTML, text/plain и JSON API с параметрами в URL |
| `search_web({query})` | Только research; один непустой строковый аргумент до 300 символов; настроенный builtin / Tavily / Brave; builtin: DuckDuckGo HTML с резервным фиксированным Bing RSS |
| `youtube_transcript({video_id})` | Только research; ровно один строковый ID из 11 допустимых символов, извлечённый сервером из пользовательских HTTPS-ссылок текущей заметки; субтитры без кадров |
| `finish_research({answer,outcome})` | Только research; формат завершения, без новых прав; ответ до 40 000 символов, outcome: complete / partial / unavailable; строгая схема, отдельный вызов без других действий |

Brave и Tavily — провайдеры одного `search_web`, а не отдельные инструменты
модели. Если модель присылает необъявленное имя, больше четырёх вызовов,
повторяющиеся ID, некорректный формат или смешивает итог с действиями,
сервер не выполняет весь этот пакет. В журнал записывается конкретная
категория отказа `tool-retry`, без сырых имён, ID, аргументов и ответа API.
Модель получает служебное требование исправить запрос и актуальный список
доступных имён. Исправление использует оставшийся бюджет исследования,
не увеличивая лимиты обращений, времени, контекста и прав. Неверная схема
итога также допускает исправление; после исчерпания бюджета остаётся явный
серверный частичный/недоступный результат. Невалидный ответ не добавляется
в историю tool calls, чтобы не отправлять API повреждённый протокол.

Вложение не читается по имени/пути от модели. Сервер сам выбирает до четырёх
последних отправленных PNG/JPEG/WebP/GIF текущей заметки и проверяет каждый
attachment ID через JOIN сообщения с note_id. Подготовленные изображения
передаются в image_url. Универсальной операции чтения файлов у модели нет;
вложения чужой заметки и ещё не отправленные загрузки недоступны.
Клиентские attachmentIds при отправке
проверяются по принадлежности текущей заметке и не могут переиспользовать чужую
или уже отправленную загрузку. Общая заметка получает собственные attachment ID
и ссылки на сохранённые файлы источников; старые BLOB-фото копируются в неё.

В `chat` инструментов нет. В `research` разрешены объявленные web tools:
валидируются имя, тип вызова, JSON-объект, точный набор ключей, тип и длина
аргумента. Все DNS-адреса должны быть публичными; выбранный IP закрепляется
при TLS-соединении. Redirect проходит проверку заново, максимум три перехода.
DNS ограничен 5 секундами, страница — 15 секундами и 1,5 МБ на переход,
результат чтения — 18 000 символов. Нет доступа к локальной сети, metadata,
file URLs, cookies, скриптам. API-провайдер использует те же проверки адреса
и запрещает redirects. Ответ API ограничен 2 МБ и 600 секундами; исследование
в целом — 660 секундами и настраиваемым количеством обращений к модели
от 4 до 12 (по умолчанию 12). До последнего ответа допускается до четырёх
tool calls на шаг; в последнем доступен только
`finish_research`. Обычный текст модели в research считается промежуточным:
сервер требует окончательный итог, не публикуя обещания продолжить как ответ.
Если итог так и не получен, сервер возвращает явное сообщение об остановке
с известными ссылками и не продолжает работу в фоне. Увеличенный лимит,
необходимость финализации и сохранённый контекст могут увеличить обычное
число обращений и входных токенов. Совместимость этого сценария с живым GLM
не проверялась платным запросом.

DNS использует отдельный отменяемый `Resolver` из Node: A и AAAA запрашиваются
параллельно, с двумя попытками DNS (1500ms на попытку) и общим пределом 5 секунд.
Отмена операции, остановка сервера и дедлайн отменяют незавершённые DNS-запросы.
Отсутствие одной семьи адресов допустимо; ошибка/таймаут этой семьи не игнорируется
даже при успешном ответе другой. Любой непубличный IP запрещает соединение.
Применяется DNS-конфигурация контейнера, без изменения DNS хоста и без внешнего
резервного резолвера. Ошибка подключения к AI теперь указывает этап и имя узла,
без URL-пути, ключа или текста заметки. Автоматического повтора AI POST нет.
API Node описан в [документации Resolver](https://nodejs.org/docs/latest-v24.x/api/dns.html#class-dnspromisesresolver).

Встроенный поиск использует максимум два фиксированных публичных источника. Если DuckDuckGo
возвращает ошибку, CAPTCHA или пустую выдачу, запрашивается
[Bing RSS](https://blogs.bing.com/search/2005/1/RSS-Feeds-for-Search-Results/).
RSS разрешён только во внутреннем пути поиска; `read_url` принимает HTML,
обычный текст и JSON. Для RSS действуют те же DNS/IP, redirect, время и
размер; в результаты проходят только проверенные HTTPS URL, максимум шесть.
Ответ инструмента сохраняет `results`/`untrusted` и добавляет `provider`.
Запрос поиска передаётся выбранным поисковым сайтам, API-ключ — нет. Это
публичные веб-выдачи без платного API, их доступность и качество не гарантированы.

`read_url` дополнительно принимает `application/json`, `text/json` и типы
`application/*+json` (например, `application/ld+json`, `application/problem+json`
или `application/vnd.api+json`). MIME сравнивается без учёта регистра и параметров.
JSON валидируется целиком в пределах сетевого лимита 1 500 000 байт; некорректный
ответ даёт явную ошибку без вывода его содержимого. В `text` передаётся исходный
JSON, без преобразования больших числовых ID в округлённые JavaScript Number.
Обычный текст также больше не проходит через HTML-парсер.

Результат сохраняет `url`, `title`, `text`, `untrusted:true` и добавляет `format`
(`html` / `text` / `json`), `contentType` и `truncated`. В контекст и архив
материалов передаётся до 18 000 символов; `truncated:true` означает фрагмент,
который может не быть самостоятельным JSON-документом. Модель предупреждена
об этом и может уточнить публичный URL/пагинацию в пределах бюджета исследования.
Загрузка по-прежнему только GET: модель не задаёт методы, заголовки, cookies,
тело запроса или серверные ключи. DNS/IP, TLS pinning, redirects, время, размер,
изоляция заметки и запрет инструментов в режимах chat/notes не меняются.

Для JSON-расширения выполнено только перечитывание изменений. Сетевые проверки
JSON, тесты и пересборка контейнера не запускались; приведённые ниже результаты
относятся к прежнему этапу проверки DNS/HTML-поиска, а не к этому расширению.

Проверка 2026-11-01: исходный пятисекундный DNS-сбой не воспроизвёлся;
в текущем контейнере lookup занял 70–155ms. DuckDuckGo подтвердил HTTP 202,
резерв Bing вернул 6 HTTPS-ссылок за 1,7s уже из установленного образа.
Проверены чтение example.com и отказ для private/file URL. Отдельные проверки
со stub Resolver покрыли дедлайн, отмену, остановку, отсутствие A/AAAA и отказ
при приватном IPv6 в смешанном ответе; stub поиска — fallback, экранирование
запроса и фильтрацию ссылок. Платные вызовы и браузер не запускались.
После перезагрузки UI восстанавливает «Повторить ответ», если последнее
сохранённое сообщение — пользовательское и AI включён; используется его же ID.

В `notes` модель не вызывается, включая превью и сортировку. В demo модель
не вызывается при любых ключах и режимах. Промпты диалога, превью и сортировки
сохранены отдельно; их редактирование не меняет серверные права.
Выполняющаяся операция использует snapshot настроек.

## HTTP-контракт и необходимые изменения интерфейса

### Галерея, видео и работа после закрытия

Новый Gallery.jsx и обновлённый AppSettings.jsx взяты из текущего checkout,
без восстановления прежних настроек, разметки или controllers навигации.
`GET /api/media?q=&limit=60&cursor=` → `{items,nextCursor}`. Карточка:
`{id,name,mime,size,noteId,title,color,createdAt,url,previewUrl}`.
Индекс объединяет прежние SQLite BLOB-фото и отправленные файловые вложения,
без чтения тела сообщений или BLOB в Node. Неотправленные загрузки не входят.
Порядок createdAt DESC / id ASC; курсор — base64url от `{at,id}`, проверяется
сервером, максимум 60 элементов. Поиск до 300 символов проверяет все слова
по имени и названию заметки с Unicode lowercase; FTS заметок сохранён отдельно.
UI использует серверный поиск и кнопку «Ещё медиа» для следующей страницы.

`GET|HEAD /api/attachments/:attachmentId/preview` выдаёт `image/jpeg` для видео.
Только attachment ID из отправленного сообщения; URL/путь от модели не принимается.
Первый запрос создаёт постер первого видеопотока, затем читается кеш
`/app/data/media/<internal-file-id>.preview.jpg`. Старые изображения используют
прежний endpoint оригинала. Плеер оригинала сохраняет Range. UI сначала
загружает JPEG лениво; при его ошибке возвращается к обычному video element
без autoplay. Никаких фиктивных картинок вместо содержимого.

Генерация — FFmpeg из Debian, фиксированный argv в C sandbox. Родитель открывает
оригинал O_NOFOLLOW, проверяет regular file/nlink/размер и передаёт только
read-only fd 3. Landlock допускает чтение этого inode и runtime-библиотек;
доступ к каталогу data/SQLite запрещён. Seccomp запрещает сеть и прежние опасные
syscalls, env пустой; формат ввода mov/matroska/webm, протоколы file/pipe,
один кадр MJPEG, scale в пределах 640×640, без аудио/субтитров/данных.
CPU 8 секунд, wall time 15 секунд на декодирование, address space 512 МиБ,
одна операция одновременно, максимум 16 ожидающих/выполняемых заданий,
вывод максимум 512 КиБ, проверка JPEG start/end. Запись через собственный
временный файл и rename, без перезаписи оригинала. При отказе — 503;
небезопасного fallback нет. Ошибочные декодирования не повторяются до рестарта
(до 512 ID в памяти). Постеры удаляются только с последней ссылкой на оригинал
при явном удалении заметки; существующие файлы автоматически не очищаются.

Кнопка прикрепления в чате использует прежний binary PUT. Сохраняет ID успешно
загруженного файла между повторами, сверяет pending metadata после неопределённой
ошибки; POST messages передаёт attachmentIds и стабильный ID сообщения.
Неполная загрузка очищает только собственный временный файл по прежнему правилу;
неотправленные завершённые файлы не удаляются автоматически. После ошибки и
перезагрузки их по-прежнему можно получить через pending API; отдельное
восстановление такого composer после полной перезагрузки не добавлено.

`GET /api/activity` → `{activity:[{noteId,agentWorking,previewPending}]}`.
Те же флаги добавлены к карточкам GET notes и GET note; GET notes также включает
activity для всей коллекции, независимо от текущего фильтра. Рабочие запросы
ответа принадлежат App, не Chat: уничтожение SendButton controller при закрытии
окна не отменяет HTTP/серверную работу. Escape в работающем чате закрывает его
до обработчика отмены SL-кнопки. Отправка ещё загружаемых файлов остаётся отдельной
блокирующей фазой. Модель не получает новых инструментов или дополнительных заметок.

POST close при занятой заметке ждёт снятия серверного lock и затем обновляет
превью по окончательной переписке; повторные закрытия объединены. UI не ждёт
этот запрос для анимации закрытия. Необязательный `{messageId}` защищает от
удаления пустого черновика до фиксации отправляемой реплики; 409 в этой гонке
повторяется приложением после завершения уже выполняемой отправки, без нового
вызова модели. Состояние карточек опрашивается раз в 1,5 секунды только при
известной работе; «Агент работает» имеет приоритет над «Обновляю превью…».
Волна — существующий PreviewStatus с параметром label и прежним reduced-motion.
Запись ответа/превью сохраняет проверки ревизий и транзакции. Ошибка AI не стирает
сообщения/старое превью; ошибка отложенного закрытия попадает в collection-notice.
Состояния и очередь живут в процессе: после рестарта незавершённая платная работа
не продолжается автоматически, уже сохранённые сообщения и медиа остаются.

Код и связанный HTTP-контракт перечитаны. Тестовые файлы, тесты, lint, typecheck,
браузер, Electron, визуальная проверка и платные API-запросы для этой правки
не выполнялись. Успешная сборка или запуск не подтверждают декодирование реальных
кодеков, сценарий закрытия с живым GLM или стойкость ограничения процесса.

Frontend исходники в runtime-образ не копируются; оформление входит в bundle.

Защита от незавершённого исследования сообщает модели оставшийся бюджет
и явно определяет конец работы.
Известные незавершённые окончания отклоняются как tool result, с исправлением
в пределах оставшихся обращений; при исчерпании бюджета возвращается прежнее
явное серверное завершение с источниками. Частичный/недоступный результат
завершается фразой об отсутствии автоматического продолжения. Проверка окончаний
эвристическая, не доказывает содержательность произвольного ответа модели.
Лимит обращений не увеличивается без выбора пользователя: это влияет на расход.
Defaults/read/public settings включают `researchMaxCalls:12`; PATCH принимает целое 4–12,
неуказанное поле сохраняет прежний выбор. Старые настройки без этого поля
получают 12 при чтении, без переписывания SQLite/ключей. Вкладка «Инструменты»
использует существующий select с выбором 4–12; сохранение без вызовов провайдера.
Адаптер берёт лимит из snapshot настроек и считает последний шаг относительно
него, а не принудительно завершает на четвёртом обращении. Оставшиеся
контекст/время/число инструментов на шаг и scope не расширены. Готовый итог
завершает работу раньше лимита, даже на первом шаге. Это повышает возможную
стоимость будущих исследований; тестовые платные обращения не выполняются.

Обработка отказов tool calls описана выше;
неизвестные операции по-прежнему не выполняются и не получают новых прав.
Перед выполнением инструментов есть отдельная runtime assert-проверка
допустимых имён, размера пакета и запрета действий в последнем шаге.

### Модели чата и анализ изображений

`GET /api/settings` возвращает `settings.model` и `settings.visionModel`.
`PATCH /api/settings` принимает их вместе с прежними полями. `model`:
`glm-5.3-long | glm-5.3 | qwen-3.8-next`; существующее неизвестное значение из
GHOSTMETAL_MODEL допускается сохранить без изменения. `visionModel`:
`same | off | glm-5.3-long | glm-5.3 | qwen-3.8-next`. По умолчанию same;
старые записи без этих полей читаются с fallback, без миграционной записи
или замены ключа. Сохранённый model имеет приоритет над env. Пропущенные
поля сохраняют прежний выбор; сохранение/чтение настроек не вызывает провайдера.
Ключ и endpoint общие для обеих моделей, secrets не возвращаются через API.

Публичный [каталог GhostMetal](https://api.ghostmetal.io/v1/models) прочитан
2026-11-01 без авторизации: у всех трёх моделей vision:true, image input,
text output и tools/tool_choice. Имена/флаги в shared/ai-models.mjs — snapshot
этого каталога, не результат платного испытания. Публичный клиент GhostMetal
также использует content parts `{type:"image_url",image_url:{url:dataUrl}}`.
`qwen-image-2.1` — генератор/редактор через Images API, не модель анализа.
Генерация/редактирование в Kakuoku этой правкой не добавляются.

В ответах chat/research сервер передаёт до четырёх последних отправленных
PNG/JPEG/WebP/GIF текущей заметки. imageForModel проверяет каждый ID по
сообщению/note_id, открывает файл O_NOFOLLOW, проверяет размер/nlink=1 и даёт
обработчику только read-only fd 3. Для старого SQLite BLOB сервер создаёт
собственный временный .vision.part в data/media и удаляет только этот
промежуточный файл после обработки; сохранённый BLOB не меняется. В C sandbox
есть отдельная фиксированная операция --image для FFmpeg: разрешены только
png_pipe/jpeg_pipe/webp_pipe/gif, первый кадр, JPEG, до 1600px без увеличения
маленьких картинок. Сеть, база и ключи worker недоступны. Сохранены пределы
8 CPU секунд, 15 секунд wall time, 512 МиБ address space и max_alloc 32 МиБ.
Дополнительно сервер ограничивает результат 1 МиБ и две одновременные
операции подготовки изображений. Сложный/повреждённый файл или ресурсный
предел приводят к ошибке без потери оригинала/сообщения, а не выдуманному описанию.

Подготовленные JPEG передаются только сервер→AI как bounded data URLs;
загрузка оригиналов через UI по-прежнему потоковая, без base64 JSON.
Текстовый контекст имеет прежний предел 350k символов, байты картинок отдельно
ограничены 4×1 МиБ. Подготовка входит в общий deadline исследования 660 секунд.
Метаданные явно помечают imageProvided; имена/хеши не считаются содержимым.
Текст внутри картинки недоверенный и не расширяет права инструментов.
Ссылки на сайты, чужие заметки, pending uploads и пути не дают доступа к файлам.

Если изображения переданы, весь текущий цикл ответа использует visionModel;
same выбирает model. Дополнительного AI-вызова на каждый файл нет. Все шаги
исследования используют тот же multimodal-контекст и могут увеличить расход
входных токенов. Превью/сортировка используют model и только текст/метаданные.
off отключает передачу пикселей; неизвестная vision-возможность env-модели
также не позволяет передавать изображения. В notes/demo модель не вызывается.
GIF понимается только как первый кадр; видео и звук не передаются.
Upload сам не анализирует содержимое: его analysis — not-requested для
изображений, unavailable для остальных типов. Это не подтверждение результата
распознавания; доступность функции описана в capabilities.media.imageAnalysis.

Пять локальных проверок с mock транспорта прошли: выбор visionModel и
реальные content parts, off/notes без чтения изображений, последние четыре
ID, остановка до модели при неверном JPEG, сохранность ключей/пропущенных
настроек и запрет генератора в visionModel. Отдельный контейнер без сети,
ключей и production volume подтвердил реальные PNG/JPEG/WebP/GIF, предел
1600px (PNG 3072×1024 → JPEG 1600×533), старый BLOB, сохранность оригиналов,
запрет чужой заметки/pending/path traversal/symlink и прежние видеопостеры.
Платные вызовы и браузер не выполнялись: реальное декодирование запроса
провайдером и качество визуальных ответов остаются неподтверждёнными.

Изолированный HTTP-прогон при разработке подтвердил сохранение обеих моделей,
отсутствие секрета в ответе, enabled/notes и сохранение прежнего потока загрузки.
Исходный API-ответ не переписывается автоматически: для нового визуального
ответа пользователь отправляет новую реплику, а не повторяет уже отвеченный ID.
Браузер, lint/typecheck, генерация, платные модели/поиск не запускались.

### Инструменты поиска и субтитров

`GET /api/settings` дополняет `settings` полем
`tools:{searchProvider,youtubeProvider,hasKeys:{tavily,brave,supadata}}`.
Значения по умолчанию: `builtin` и `local`. Старые настройки не перезаписываются;
при чтении к ним добавляются эти значения. Старый клиент без поля `tools`
может сохранять остальные настройки, не стирая инструменты и их ключи.
Новый `PATCH /api/settings` принимает вместе с прежними полями
`tools:{searchProvider,youtubeProvider,keys?:{tavily?,brave?,supadata?},clearKeys?:[]}`.
Провайдеры: поиск `builtin|tavily|brave|off`, YouTube `local|supadata|off`.
Указанный ключ должен быть непустой строкой до 4096 печатных ASCII-символов
без пробелов; неуказанные ключи сохраняются. `clearKeys` содержит имена ключей
для удаления; одновременно заменять и удалять один ключ запрещено.
Сохранение не выполняет сетевые запросы. Secrets не возвращаются в GET/PATCH,
не включаются в промпты и не передаются worker. UI хранит введённый ключ
в памяти компонента до сохранения/закрытия, без localStorage.

`GET /api/capabilities` дополняется `tools`: выбранные провайдеры и hasKeys,
списки поддерживаемых провайдеров, `youtubeScope:"user-links-in-current-note"`,
`youtubeUnderstanding:"captions-only"`. `agent.tools` — список поддерживаемых
операций, а не разрешение в текущем режиме: фактический набор формируется
для каждого запроса. `search_web` отсутствует при off; `youtube_transcript`
объявляется только при включённом провайдере и наличии разрешённых ссылок.
Имена и строгие схемы проверяются независимо от промпта. Для субтитров сервер
повторно проверяет ID по сообщениям с role=user текущего snapshot заметки.
Ссылки модели, найденные сайты и другие заметки не расширяют этот список.

Tavily: фиксированный `POST https://api.tavily.com/search`, bearer key,
basic, до 6 результатов, без AI answer/raw content/auto parameters.
Brave: фиксированный `GET https://api.search.brave.com/res/v1/web/search`,
X-Subscription-Token, до 6 результатов. Возвращаются только проверенные
публичные HTTPS URL и ограниченные текстовые поля. API endpoints не задаются
моделью. Transport использует прежние DNS/public-IP checks, закреплённый IP,
20 секунд на запрос, 1,5 МБ ответа, без redirects и без возврата тела ошибки
провайдера (в нём могут быть секреты). Выбор внешнего API может расходовать
его платные квоты; fallback на платный сервис отсутствует.

Локальный YouTube: Python 3 + venv `/opt/kakuoku-youtube`, библиотека
`youtube-transcript-api==1.2.4`, зависимости в `server/requirements-youtube.txt`.
Python запускается фиксированными аргументами `-I -B youtube-worker.py` через
существующий C sandbox; subprocess не получает окружение, ключи или SQLite.
Landlock запрещает data и запись, seccomp — socket/connect/ptrace и прежние
опасные syscalls; 3 CPU-секунды, 256 МиБ address space, 60 секунд wall time.
Если sandbox недоступен, небезопасного fallback нет. Сеть worker заменена
stdio-брокером: сервер разрешает максимум 6 запросов, только HTTPS YouTube
`/watch`, `/youtubei/v1/player`, `/api/timedtext`, с тем же video ID,
не более 3 МБ на ответ и без redirects. Только эфемерный consent cookie,
без cookies аккаунта. Публичный Innertube client key извлекается библиотекой
из страницы; это не пользовательский API-ключ. В контейнере нет yt-dlp,
скачивания видео, headless browser, ffmpeg или speech recognition для этого пути.

Supadata: фиксированный `GET https://api.supadata.ai/v1/transcript`,
каноническая ссылка разрешённого YouTube ID, `mode=native`, timestamped chunks.
Ответ с jobId опрашивается не более 10 раз с интервалом 1,5 секунды на том же
фиксированном сервисе; общий предел 60 секунд. Нет `auto`/`generate` или платного
fallback. Ни произвольные URL, ни локальные медиа этому сервису не отправляются.

Оба варианта возвращают `{url,title,provider,language,generated,segments:[
{text,start,duration}],truncated,understanding:"captions-only",untrusted:true}`;
времена в секундах. До 32 000 символов и 1000 сегментов; обрезка помечена.
Результат сохраняется в research_materials как остальные инструменты.
Субтитры — недоверенные данные; ответ обязан различать речь и кадры. Нет
субтитров / IP block / приватное или возрастное ограничение → явная ошибка,
а не выдуманное распознавание. Все прежние режимы и scope сохраняются.

Источники: [youtube-transcript-api](https://github.com/jdepoix/youtube-transcript-api),
[PyPI 1.2.4](https://pypi.org/project/youtube-transcript-api/),
[Tavily Search](https://docs.tavily.com/documentation/api-reference/endpoint/search),
[Brave Search](https://api-dashboard.search.brave.com/app/documentation/web-search/get-started),
[Supadata transcript contract](https://github.com/supadata-ai/skills/blob/main/skills/supadata/references/video.md).

не решает чтение чужого Shorts. Более широкий

но для этой задачи не подключён: нужен только ограниченный доступ к субтитрам.

Новая интеграция перечитана по исходникам. Запросы к GLM, Tavily, Brave,

Тесты, lint, typecheck, браузер и source audit новых UI-подключений не запускались.
Сборка образа устанавливает Python-библиотеку и зафиксированные зависимости.
Успех сборки не подтверждает работу субтитров на реальном YouTube,
успешность платных API или стойкость sandbox.

Текущие session/settings/profile/notes/messages/reply/close/summary/sort
маршруты и JSON-поля сохранены. Добавлены поля `sources` заметки и `size`
вложения; старые клиенты могут их игнорировать. Отображать текст пользователя,
модели и имена вложений только как недоверенный текст; не использовать innerHTML.
Переписка отображает CommonMark и GFM через `react-markdown` + `remark-gfm`:
списки, выделение, цитаты, блоки кода, таблицы, task lists и ссылки. HTML
игнорируется (`skipHtml`), `innerHTML` не используется. Ссылки допускают только
HTTP/HTTPS и якоря; картинки из Markdown показываются текстом alt, без внешней
загрузки. Пользовательские вложения отображаются отдельно, по прежнему API.

POST messages по-прежнему возвращает полную заметку после завершения AI,
без streaming/SSE. Пока запрос выполняется, UI показывает локальную отправляемую
реплику и временный бабл с тремя точками, если AI включён. При ответе API
локальная реплика заменяется серверной; при сетевой ошибке/отмене текст и файлы
возвращаются в composer с прежним idempotency ID. Ошибка AI с сохранённым
сообщением оставляет серверную реплику и кнопку повтора. Индикатор также работает
при повторе ответа, но не появляется при изменении оформления или в режиме записи.

В этот же бабл включены текущее действие и раскрываемый журнал «Ход работы».
UI опрашивает `GET /api/notes/:id/research?messageId=<uuid>` раз в секунду
пока ожидает ответ. Параметр необязателен; без него возвращается последний
запуск заметки. Ответ: `{research:null}` или `{research:{id,messageId,state,
events:[{kind,text,at}],updatedAt,expiresAt}}`. Состояния: `running`, `complete`,
`partial`, `unavailable`, `error`, `interrupted`. Чужой messageId не возвращает
журнал другой заметки. Это только серверные события действий, без reasoning,
сырых материалов, секретов или настроек. `GET /api/notes/:id` также включает
`research`; при `busy:true` и `running` UI восстанавливает опрос после перезагрузки,
не повторяя платный запрос. Завершённый журнал доступен через API; UI скрывает
временный бабл после ответа. Три последовательных ошибки опроса восстановленной
операции показывают предупреждение и освобождают интерфейс.

Журнал и успешные результаты веб-инструментов хранятся в новых таблицах
`research_runs` и `research_materials` в той же SQLite внутри `/app/data`.
Ответ ассистента и финальное состояние запуска записываются одной транзакцией;
повтор уже отвеченного messageId не запускает модель и не дублирует ответ.
Материалы ограничены текущей заметкой и активной группой запусков: окно —
30 минут после последнего отправленного сообщения или события обработки.
Чтение UI/API не продлевает его. Смена режима на chat не снимает ограничения
текущей заметки; ещё активные материалы можно использовать без новых web calls.
В notes модель и журнал нового AI-запуска не вызываются.
В контекст выбираются до 50 последних материалов группы, до 80 000 символов
и в пределах общего лимита 350 000 символов JSON-контекста. Переписка передаётся
заново при каждом обращении: провайдерская сессия или keepalive для этого не нужны.
Истечение окна начинает новую группу, не удаляя прежние материалы и сообщения.
Явное удаление заметки удаляет её журнал и материалы каскадно. Остановка сервера
не удаляет их; при следующем старте `running` становится `interrupted`, без
автоматического повтора и продления окна. Эта миграция добавляет таблицы,
не пересоздаёт заметки и не переносит хранилище.

Сначала `GET /api/session` → `{token,demo,agentEnabled,model}`. Для всех
изменяющих запросов обязателен заголовок `X-Kakuoku-Token`. Host должен совпадать
с `localhost:3101` или `127.0.0.1:3101`; проверяются Origin и Sec-Fetch-Site.
GET-навигация верхнего окна к интерфейсу разрешена и по внешней ссылке
(`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`). Исключение не
распространяется на `/api/`, iframe, загрузку ресурсов или изменяющие запросы.
Произвольного CORS нет. После перезапуска token меняется — клиент получает
403 и должен обновить сессию. В production настройки внешнего порта сервера
и публикация Compose должны совпадать. Локальный пользователь с прямым доступом
к порту доверенный; это защита от чужих сайтов, а не многопользовательская auth.

`GET /api/capabilities` возвращает лимиты/типы медиа, режимы, область данных
агента и `media.analysis: "images"`, `agent.mediaUnderstanding: true`,
`agent.mediaKinds:["image"]`. `media.imageAnalysis` содержит enabled, model,
types, maxImages:4, maxEdge:1600, maxBytesPerImage:1048576, gif:"first-frame".
enabled=false в demo/notes, без ключа, при выключении vision или неизвестной
мультимодальной поддержке выбранной модели. Видео и звук не анализируются.
Поле `research` сообщает `windowSeconds:1800`, `finalization:"finish_research"`
и актуальный `maxModelCalls` из настроек (по умолчанию 12),
`minAllowedModelCalls:4`, `maxAllowedModelCalls:12`, `timeoutSeconds:660`.
Кнопка прикрепления, ошибки загрузки, проигрыватели audio/video и галерея
подключены к этому API. Отдельного процента загрузки и восстановления
неотправленного composer после полной перезагрузки пока нет. Загрузка сама
не вызывает анализ; JPEG-копии изображений передаются только при ответе AI
с включённым vision. Дизайн и controllers навигации сохранены.

### Потоковое вложение

1. Создать/открыть заметку обычным API.
2. Сгенерировать UUID для загрузки.
3. `PUT /api/notes/:noteId/attachments/:uploadId` с телом `File`/`Blob` или
   бинарным потоком, `Content-Type: application/octet-stream`,
   `X-Kakuoku-Filename: encodeURIComponent(file.name)` и session token.
   Content-Length необязателен: chunked upload тоже ограничен по факту байтов.
4. Получить 201 `{attachment:{id,name,mime,size,sha256,analysis:"unavailable"}}`.
5. Отправить сообщение по прежнему маршруту с новым полем:

```json
{"id":"UUID сообщения","text":"Описание","attachmentIds":["UUID загрузки"],"revision":3}
```

Старое поле `attachments:[{name,data:base64}]` остаётся только для малых
PNG/JPEG/WebP существующего UI. Не передавайте через него аудио/видео.
Общее число старых фото и новых attachmentIds — максимум четыре.
В `note.messages[].attachments` вернутся **ID привязок к сообщению**; это
отдельные UUID, не upload ID. Для выдачи используется именно ID из сообщения.

`GET /api/notes/:noteId/attachments` → `{attachments:[{id,name,mime,size,sha256}]}`:
неотправленные загрузки. Повторный PUT с тем же ID возвращает 409, не
перезаписывая файл: при потере ответа получите этот список. До отправки
просмотр выполняйте через локальный Object URL выбранного файла.
`DELETE /api/notes/:noteId/attachments/:uploadId` явно удаляет неотправленный
файл; привязанный к сообщению получает 409.

Предел: 128 МиБ на файл, 16 неотправленных файлов на заметку, две параллельные
загрузки во всём сервисе, 120 секунд на загрузку. Суммарный лимит новых медиа
в SQLite-реестре — 2 ГиБ (BLOB старого API, переписка и crash-orphans в него
не входят). Это не дисковая квота Docker volume; следите за свободным местом.
Файл больше лимита → 413, неподдерживаемая сигнатура → 415, перегрузка → 429,
конфликт заметки/ID → 409. При ошибке UI сохраняет текст и выбранные файлы.
Ошибка запуска, падение, таймаут или повреждённый ответ детектора → 503;
они не выдаются за неподдерживаемый формат. Clipboard, drop в открытом чате
и file input передают настоящие File через один загрузчик. Из DataTransfer
сначала читаются file items, затем FileList, без удвоения одних и тех же файлов.
Браузерный MIME не отбрасывает файлы на клиенте; лимиты размера и количества
проверяются и клиентом, и сервером. Текст/HTML/URL из буфера не становятся
файлом и не запускают автоматическую сетевую загрузку.

Поддерживаются сигнатуры PNG, JPEG, WebP, GIF, MP4/M4A, WebM, MP3, WAV, FLAC,
Ogg/Opus. Конкретные MIME перечислены в capabilities. Расширение и присланный
MIME не используются для определения формата. Первые 64 КиБ проверяет
`file-type` в Node subprocess с `--permission` и дополнительным нативным
launcher `media-sandbox.c`. Launcher непривилегированно устанавливает Landlock:
разрешены только бинарник Node, системные библиотеки, код детектора,
package.json, node_modules и несколько файлов runtime.
Для старта Node также разрешено чтение только `/etc/ssl/openssl.cnf`:
без него OpenSSL завершал процесс с кодом 13 до чтения заголовка файла.
Остальные системные конфигурационные каталоги не открываются целиком.
`audio/x-m4a` и `audio/ogg; codecs=opus` от file-type приводятся к
`audio/mp4` и `audio/ogg` соответственно, только после распознавания байтов.
`/app/data` и окружение родительского процесса в `/proc` недоступны.
Seccomp блокирует sockets/сеть,
ptrace, process_vm, получение чужих fd и io_uring. Проверка запрета чтения data
и открытия socket встроена в launcher; без успешной установки ограничений
он не запускает Node. Процесс получает ограниченный буфер по stdin,
пустое окружение, heap 32 МиБ, CPU 3 секунды, timeout 5 секунд; не получает
файл, API-ключ или дескриптор базы. Унаследованные fd, кроме stdin/stdout/stderr,
закрываются launcher до запуска детектора. Команда фиксирована приложением,
у модели её нет.
Node Permission Model — дополнительный слой: он сам по себе не гарантирует
запрет всех способов чтения (в частности, через node:sqlite).
Нужны Linux с включённым Landlock (ABI >= 1, kernel >= 5.13) и разрешение
установить Landlock/seccomp внутри Docker; launcher собирается для amd64/arm64.
Если это недоступно, API возвращает 503 и не использует небезопасный fallback.
На хостовой дизайн-демке launcher не установлен: прежний API малых фото работает,
новый потоковый путь требует production-образа. Launcher скомпилирован при сборке;
после исправления OpenSSL прошёл интеграционную HTTP-проверку в отдельном
контейнере с non-root, read-only, no-new-privileges, cap_drop и без сети.
11 реальных форматов PNG/JPEG/WebP/GIF/MP4/WebM/WAV/M4A/MP3/FLAC/Opus прошли
потоковую загрузку, привязку к сообщению, побайтовую выдачу, Range 206 и индекс
галереи. Расширение всех файлов намеренно было .jpeg; текст под .jpeg получил
415 и не остался в реестре. Повтор сообщения не создал дубликаты. Прямые
проверки transferFiles/hasFileTransfer прошли; тестовые данные находились
только в tmpfs отдельного контейнера без production volume и ключей.
Платные запросы и браузер не запускались. Это подтверждает данный медиапуть
на текущем Docker/ядре, но не стойкость к kernel/runtime escape, все кодеки
или реальные события буфера и drop в браузере пользователя.

Неотправленный черновик в текущей вкладке не переносится при перезагрузке
frontend — перед обновлением страницы нужно скопировать текст.
Это определение бинарной сигнатуры, **не** полное декодирование/антивирус;
необычный или длинный заголовок может быть отклонён. Совместимость кодека
с воспроизведением зависит от браузера. Транскодирование не реализовано.

`GET|HEAD /api/attachments/:attachmentId` выдаёт файл с nosniff, CSP sandbox,
без directory listing, без пути от клиента. `Range: bytes=start-end`, `start-`
и `-suffix` дают 206 с Content-Range; обычный запрос — 200, некорректный или
множественный диапазон — 416 с `Content-Range: bytes */size`. Файл читается
потоком. Финальный путь построен только из серверного UUID; O_NOFOLLOW,
проверка обычного файла/размера/числа hardlinks запрещают подмену symlink.
Корень медиа проверяется при старте. `/app/data` и секреты никогда не static root.

### Ревизии и повтор запросов

`note.revision` меняется при сообщениях и метаданных. Смена оформления или
заголовка сама по себе не запускает повторную генерацию уже актуального превью.
Новые клиенты передают
ожидаемую `revision` в PATCH заметки и POST messages; DELETE заметки принимает
`If-Match: "3"`. Несовпадение → 409, UI перечитывает заметку и сохраняет локальный
ввод для решения пользователя. Для совместимости старые запросы без ревизии
принимаются; защита от устаревшего редактирования между двумя вкладками для
них ограничена сериализацией, поэтому frontend следует подключить revision.

Переименование доступно и во время ответа агента: только PATCH с единственным
изменяемым полем `title` может пройти через блокировку активного ответа.
Интерфейс передаёт также `previousTitle` — название на момент начала
редактирования. Несовпадение с текущим названием даёт 409, без перезаписи
чужого переименования. Явная `revision` по-прежнему проверяется; без неё сервер
проверяет актуальную ревизию внутри транзакции. Ответ AI добавляется по текущей
ревизии: смена заголовка не отменяет его сохранение. Остальные изменения,
удаление и новые сообщения по-прежнему сериализованы с работой агента.

UUID сообщения является idempotency key. Новый запрос сохраняет сообщение
транзакционно **до** AI; повтор того же содержимого не создаёт новое сообщение
или второй ответ. Использование того же ID с другим содержимым → 409.
Для исторических сообщений без request_hash сохраняется прежняя совместимость.
Ответ записывается с проверкой ревизии и уникальным reply_to. Ошибка AI возвращает
сохранённую заметку, warning и retryMessageId; повтор — POST reply с messageId.
Предыдущее превью при ошибке AI не изменяется. Пустой черновик при close удаляется,
первое отправленное сообщение закрепляет заметку. Повторное close/summary на
актуальной ревизии с теми же правилами превью не обращается к AI и не создаёт
сводку заново. `summary_key` — fingerprint правил, промпта, модели и endpoint
без ключа API. Миграция добавляет этот столбец без переписывания сообщений.
Старое превью остаётся до следующего явного закрытия, которое обновляет его
по новым правилам; на старте и при сохранении настроек модель не вызывается.

Frontend закрывает диалог без ожидания ответа `POST /api/notes/:id/close`.
Запросом и его результатом управляет лента: по завершении перечитывает карточки,
при ошибке показывает уведомление. Карточка помечает ожидание текстом
«Обновляю превью…». HTTP-контракт остаётся синхронным, но долгой блокировки
заметки при подготовке превью больше нет: сервер работает со snapshot, а запись
проверяет revision. При изменении заметки или её удалении результат snapshot
не записывается. Повторные запросы одной ревизии/правил делят один AI-вызов;
явное закрытие более новой ревизии ждёт текущий вызов и готовит новое превью.
`GET /api/notes/:id` дополнительно возвращает `previewPending`; поле `busy`
по-прежнему обозначает блокирующие операции, например ответ в чате.
Закрытие диалога не прерывает запрос. Перезапуск сервера может прервать
генерацию; прежнее превью и переписка сохраняются, автоматического платного
повтора нет.

Правила AI-превью требуют начинать с актуального итога и учитывать последние
явные исправления статуса пользователем. Закрытые задачи остаются кратким
результатом, а не подробным пересказом прежнего баг-листа. Пользовательские
настройки промптов сохраняются. Семантическое качество нового ответа модели
не подтверждено: платные проверки не выполнялись.

`POST /api/sort` принимает старое `{}` либо `{id:"UUID операции"}`. Явный ID
сохраняет статус на диске и возвращает прежний результат при повторе.
`GET /api/sort` возвращает последнюю операцию; закрытие окна её не отменяет.
Если уже выполняется другой запрос, POST возвращает его текущий job/ID.
После перезапуска running отмечается error, автоматического платного повтора
нет. Ранее созданные группы сохранены; одинаковый набор source ID/версий
неизменяемой переписки защищён уникальным merge key (как прежде, число сообщений
задаёт версию истории; смена оформления не создаёт дубль).
Полные ревизии проверяются внутри транзакции, изменённые
или удалённые источники пропускаются. Есть состояние частичного результата:
created/skipped и ошибка. Исходники и вложения сохраняются; новая заметка
содержит `sources:[{source_id,title,revision}]` даже после удаления исходника.

Сначала один запрос предлагает только группы `{ids,title}`, затем отдельный
запрос на каждую новую группу пишет обычный текст нового чата, до 20000 символов.
Длинный текст не разбирается как JSON: кавычки, переводы строк и код внутри
заметки не требуют JSON-экранирования со стороны модели. Короткие
`{summary,tags}` создаются существующим обработчиком AI-превью по готовому
тексту. Планирование и написание имеют бюджет 32768 выходных токенов;
превью сохраняет свой лимит 8192. Автоматических повторов нет:
один запрос планирования плюс два на каждую ещё не собранную группу.
Изменившиеся или уже собранные группы проверяются до генерации и ещё раз
в транзакции записи. Статус текущей группы сохраняется перед ожиданием модели;
ошибка поздней группы не удаляет уже созданные чаты.

В планировании участвуют и исходные чаты, и ранее созданные сводки. Модель
получает текущую дату, `updated_at`, время последнего пользовательского
сообщения и происхождение сводок. Служебная пара сообщений, создающая сводку,
не считается взаимодействием пользователя. Историю просмотров приложение не ведёт.
Темы и критерии давности задаёт сохранённый промпт сортировки; код не назначает
срок устаревания. Сервер объединяет вложения группы и убирает повторные ссылки
на один media file ID и одинаковые старые BLOB-вложения (имя, MIME и байты).
Исходные заметки и файлы не удаляются. Ограничение входного контекста 350000
символов остаётся; большие блокноты автоматически на части не разбиваются.

## Проверка API-провайдера и оставшиеся ограничения

По [GhostMetal docs](https://www.ghostmetal.io/docs) подтверждены endpoint
`/v1/chat/completions`, Bearer auth и OpenAI-совместимый формат. Публичный пример
указывает `glm-5.3`; существующий выбор Kakuoku `glm-5.3-long` сохранён, доступность
этого ID у конкретного ключа без обращения к API не подтверждена.
Документация описывает генерацию изображений и синтез речи, что не подтверждает
vision/распознавание видео или транскрипцию для выбранного GLM. Медиа в запросы
модели не отправляются; извлечения кадров, OCR и ASR нет. Не показывайте в UI
состояние «распознано» и не подменяйте его выдуманным результатом.

Детектор [file-type](https://github.com/sindresorhus/file-type) сам описывает
проверку сигнатур как best effort. Ограничения запуска соответствуют
[полям Docker Compose](https://docs.docker.com/reference/compose-file/services/),
но их применение конкретным Docker/kernel требуется отдельно подтвердить.
Границы медиапроверки опираются на [Landlock API ядра Linux](https://docs.kernel.org/userspace-api/landlock.html)
и [ограничения Node Permission Model](https://nodejs.org/api/permissions.html).

Фактически выполнены: чтение применимых инструкций, README, серверного кода и
клиентских вызовов; чтение документации провайдера, Docker, Node и file-type;
обновление package-lock через npm с `--package-lock-only --ignore-scripts`;
перечитывание изменений. Git-репозитория в этом каталоге не обнаружено,
поэтому git diff недоступен. При последующих исправлениях обновлён frontend:
оптимистичная отправляемая реплика, временный бабл ожидания и Markdown.
Пользовательские тексты, настройки и данные не переписывались. Выполненные
сборка и проверки текущего образа перечислены в начале документа; визуальные
и платные проверки остаются отдельным шагом по запросу пользователя.

Исправление закрытия от 2026-11-01: образ пересобран и установлен на 3101.
Через HTTP подтверждены новая выдаваемая сборка и удаление только специально
созданного пустого проверочного черновика, без модели. На отдельной временной
SQLite со stub AI проверены задержанный ответ, параллельное редактирование,
устаревшая ревизия, повторный запрос, очередь новой ревизии, ошибка, удаление,
режим notes, FTS и миграция прежней схемы. Обработчик закрытия отдельно выполнен
без браузера с незавершающимся stub-запросом превью: завершился без ожидания.
Реальный ответ GLM по новым правилам не запрашивался; точный визуальный сценарий
пользователя в браузере не проверялся.

На отдельной временной SQLite и stub-модели assert-проверками подтверждены:
поиск → чтение → явный итог, повторное использование материалов, область

Отдельный HTTP fixture с реальными обработчиками и stub-моделью подтвердил
