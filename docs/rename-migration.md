# Переход на Kakuoku с сохранением данных

Прежнее имя проекта — `mochi`, текущее — `kakuoku`.
Инструкция описывает переход существующей установки с сохранением данных;
расположение клонированного репозитория выбирает пользователь.

## Существующая SQLite

Новые базы называются `kakuoku.sqlite`. Единственное прежнее имя в исполняемом
коде — `mochi.sqlite` в `server/store.mjs`: это совместимый выбор существующей
базы, а не создание копии или автоматическое переименование.

Сервер проверяет оба семейства файлов, включая `-wal` и `-shm`. Если существует
только прежнее семейство, открывает именно его. При наличии обоих семейств или
WAL/SHM без основного файла останавливается с ошибкой, не создавая новую базу
и не выбирая одно из двух хранилищ молча.

Если демо создано прежней версией, его файлы остаются `.data/demo/mochi.sqlite`,
`.data/demo/mochi.sqlite-wal`, `.data/demo/mochi.sqlite-shm`.
Их не требуется переименовывать ради перехода на новое название проекта.

Для существующего production volume действует та же совместимость.
Не переименовывайте отдельный файл SQLite во время записи. Не удаляйте WAL/SHM:
они могут содержать ещё не перенесённые в основной файл записи. Приложение
не требует физического переименования старой базы; безопасный переход —
оставить всё семейство под существующим именем и подключить прежнее хранилище.
Промпты, API-ключи, комментарии Agentation и любые сохранённые тексты не
переписываются ради замены названия; прежнее имя может сохраняться в этих
пользовательских/исторических данных.

## Существующее Docker-развёртывание

Для ранее созданной установки сначала выполните переход ниже. Не создавайте
новый пустой volume вместо существующего с заметками.

1. По `docker ps -a` найдите фактическое имя прежнего контейнера. Остановите
   только его через `docker stop <имя-контейнера>`. Аналогично остановите
   принадлежащую приложению демку и Electron, если они работают. Не используйте
   широкие `pkill node` и не останавливайте посторонние сервисы.
2. До изменения запуска сохраните весь `/app/data`, включая SQLite/WAL/SHM
   и `media`, из остановленного контейнера:

   ```sh
   mkdir -p .data/backups
   docker cp -a <имя-контейнера>:/app/data ./.data/backups/kakuoku-backup-before-rename
   ```

   Копия содержит секреты. Не выводите её содержимое в логи и не помещайте
   в репозиторий. Убедитесь, что она сохранена, прежде чем продолжить.
3. Определите фактически подключённое хранилище, не читая environment с ключами:

   ```sh
   docker inspect --format '{{range .Mounts}}{{if eq .Destination "/app/data"}}{{.Type}} {{.Name}} {{.Source}}{{end}}{{end}}' <имя-контейнера>
   ```

   Для прежнего Compose ожидается именованный volume `mochi-production-data`.
   Проверьте его наличие: `docker volume inspect mochi-production-data`.
   В `.env` нового каталога задайте только выбор уже существующего хранилища:

   ```dotenv
   KAKUOKU_DATA_VOLUME=mochi-production-data
   ```

   Если volume называется иначе, укажите фактическое имя. Это намеренный
   совместимый идентификатор существующих данных, а не новое название приложения.
   Docker не переименовывает volume; его физическое имя сохраняется. В Compose
   он объявлен external: отсутствие выбранного volume приводит к ошибке запуска.
   Это поведение описано в [Docker Compose volumes](https://docs.docker.com/reference/compose-file/volumes/#external).
4. Из корня клонированного репозитория соберите новый образ и запустите новый
   Compose project `kakuoku` по обычной инструкции. Старый контейнер должен
   оставаться остановленным. Новые образ, контейнер и сеть получат новый
   префикс; данные будут взяты из прежнего volume, а не из нового пустого.
   Старые контейнеры, сети, образы и volumes не удаляйте для переименования:
   они остаются доступными для отдельного решения и отката.

Если `/app/data` находился в writable layer старого контейнера, либо inspect
показывает bind mount, не запускайте новый сервис с пустой базой. После остановки
сохраните каталог целиком командой выше (для Podman — `podman cp -a`), затем
восстановите копию в новый выделенный volume по разделу резервного копирования
в [backend.md](backend.md). Сначала создаётся контейнер без запуска, копируются
данные с владельцами UID/GID 1000:1000, и только затем запускается приложение.
Не подключайте домашние каталоги и не удаляйте прежний источник данных.
Автоматического переноса или удаления production-данных при переименовании нет.

## Имена и перезапуск

Свои env-переменные приложения используют только `KAKUOKU_`:
`KAKUOKU_PRODUCTION`, `KAKUOKU_PUBLIC_PORT`, `KAKUOKU_URL`,
`KAKUOKU_DATA_VOLUME`. Провайдерские `GHOSTMETAL_API_KEY` и `GHOSTMETAL_MODEL`
остались прежними; значения ключей не менялись. Внешние launcher/systemd/.env
с прежними именами нужно обновить отдельно, не перепечатывая секреты в чат.

HTTP-заголовки клиента и сервера согласованно заменены на `x-kakuoku-token`
и `x-kakuoku-filename`. После обновления нужен перезапуск сервера и перезагрузка
старых вкладок; старый открытый UI с прежним заголовком не совместим с новым
сервером. Также перезапустите Electron, если он был открыт. Порты остались 3100
для демо и 3101 для приложения; origin браузера не меняется, его хранилище не
очищается. Agentation остаётся сторонней зависимостью, его комментарии сохранены.

## Намеренно оставшиеся прежние упоминания

- `server/store.mjs`: только имя `mochi.sqlite` для обнаружения/чтения прежней базы.
- Этот документ: прежний каталог, семейство файлов и volume для инструкции
  перехода и инвентаризации сохранённых данных.
- `.data/`: исходные имена файлов и содержимое пользовательской базы сохранены.
- `node_modules`, `dist`, `.git`: исключены из замены; сторонние и генерируемые
  файлы не переписываются. При наличии старой сборки требуется обычная пересборка.

В остальных исходниках, настройках запуска и основной документации старое имя
не используется.
